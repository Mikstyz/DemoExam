# Чудо Обувь REST API

REST API учебного проекта «Чудо Обувь» на Python, FastAPI, SQLModel и PostgreSQL.
Доступ к базе выполняется через ORM-модели и SQLModel Session; отдельные SQL-запросы вручную писать не нужно.

## Возможности

- Вход по логину из таблицы `users`, без пароля и JWT.
- Каталог с поиском по названию/описанию, фильтром по категории и подкатегории, сортировкой по цене.
- Отдельные справочники категорий и подкатегорий.
- CRUD карточек товаров и изменение складских остатков для менеджера и администратора.
- Скидка 25% для товаров без заказов за предыдущий календарный месяц.
- Создание заказа из нескольких позиций, фиксация цены и уменьшение остатков в одной транзакции.
- Пользователь видит только собственные заказы; менеджер видит все заказы и может создавать/удалять их; администратор также может менять дату заказа, удалять позиции и менять их количество.

## Структура

- `model/` — SQLModel-модели таблиц.
- `repositories/` — операции доступа к данным.
- `services/` — бизнес-логика, например расчёт скидки.
- `api/` — HTTP-маршруты FastAPI и проверка ролей.
- `db/` — подключение к PostgreSQL и создание таблиц.
- `schemas.py` — схемы входных и выходных данных API.
- `config.toml` — единый файл настроек API и скриптов.
- `scripts/import_data.py` — импорт исходных XLSX в PostgreSQL.
- `import_data/` — пять Excel-файлов для первоначального заполнения БД.
- `Product.image_path` хранит путь `/media/products/<имя-файла>`. Изображения обслуживает backend из `backend/data/products/`; заглушка frontend находится в `frontend/public/images/picture.png`.

## Запуск

1. Создайте пустую базу PostgreSQL `chudo_obuv`.
2. Откройте `config.toml` и укажите строку подключения к PostgreSQL вместо шаблона `USER:PASSWORD`. Пока остались шаблонные значения, приложение остановится с понятной ошибкой.
3. Создайте виртуальное окружение и установите зависимости:

   ```bash
   python -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```

4. Первоначально заполните БД данными из Excel (выполнять из корня проекта):

   ```bash
   python -m scripts.import_data
   ```

   Скрипт загружает пользователей и роли, категории и подкатегории, товары, размеры, актуальные остатки и историю заказов. Он не уменьшает складские остатки повторно на основании импортированной истории. Историческая цена каждой позиции заказа берётся из `Orders_import.xlsx`.

   Если в БД уже есть данные и ты действительно хочешь полностью заменить их импортом, используй `python -m scripts.import_data --reset`. Флаг `--reset` удаляет текущие данные приложения перед загрузкой. Без этого флага скрипт остановится, если обнаружит существующих пользователей, товары, размеры или заказы.

   При необходимости можно указать другую папку с файлами: `python -m scripts.import_data --input-dir /путь/к/xlsx`. В папке должны лежать все пять файлов с исходными именами.

5. Запустите API:

   ```bash
   uvicorn main:app --reload
   ```

6. Swagger доступен по адресу `http://127.0.0.1:8000/docs`.

При запуске `SQLModel.metadata.create_all()` создаёт отсутствующие таблицы. Он не меняет существующую схему старой таблицы `products`. После перехода со старой версии создайте новую пустую БД либо подготовьте миграцию и импортируйте данные заново.

## Учебная авторизация без JWT

`POST /api/auth/login` принимает `{ "login": "логин_из_таблицы_users" }` и возвращает данные пользователя, включая `user_id` и `role`. Для защищённых запросов клиент передаёт `X-User-ID: <user_id>`. Например, в Swagger добавьте заголовок `X-User-ID` в запросе.

Это упрощённая схема для учебного задания, где вход происходит только по логину. Она не обеспечивает настоящую аутентификацию: клиент может подставить чужой ID. Не использовать как защиту публичного сервиса.

## Основные маршруты

- `POST /api/auth/login`, `GET /api/auth/me`
- `GET /api/products`, `GET /api/products/{product_id}`
- `POST /api/products`, `PATCH /api/products/{product_id}`, `DELETE /api/products/{product_id}`
- `PUT /api/products/{product_id}/stock/by-value`
- `PUT /api/products/{product_id}/stock/{size_id}`
- `GET/POST /api/categories`, `PATCH/DELETE /api/categories/{category_id}`
- `GET/POST /api/subcategories`, `PATCH/DELETE /api/subcategories/{subcategory_id}`
- `GET /api/orders/my`, `GET /api/orders`, `POST /api/orders`, `GET /api/orders/{order_id}`
- `DELETE /api/orders/{order_id}`, `PATCH /api/orders/{order_id}/date`
- `DELETE /api/orders/{order_id}/items/{order_item_id}`, `PATCH /api/orders/{order_id}/items/{order_item_id}?quantity=2`

Каталог поддерживает параметры `category_id`, `subcategory_id`, `search`, `sort=price_asc|price_desc`.

## Данные

Таблицы создаются автоматически, но данные пользователей, ролей, категорий, товаров, размеров, остатков и заказов должны быть импортированы. В папке `import_data/` в корне backend хранятся исходные файлы импорта. В `Orders_import.xlsx` одно название товара отсутствует в каталоге полностью. Для него скрипт создаёт минимальную карточку на основе истории заказов, без изображения и подкатегории. Если название товара в заказе отличается от названия в каталоге только дополнительным уточнением в конце, скрипт использует существующую карточку при условии однозначного совпадения производителя.

Важно: `create_all()` создаёт отсутствующие таблицы, но не мигрирует старую схему. Если существующая таблица `products` ещё содержит текстовые поля `category`/`subcategory` вместо `category_id`/`subcategory_id`, сначала используй новую пустую БД или подготовь миграцию. `--reset` очищает данные, но не изменяет структуру уже созданных таблиц.

### Изображения товаров

Поле `Изображение` из `Products_import.xlsx` импортируется как имя файла, например `IMG_KS_195217.png`. Эти изображения должны находиться в `backend/data/products/`, откуда backend отдаёт их через `/media/products/`. Для товаров, восстановленных из истории заказов и не имеющих изображения в исходных файлах, `image_path` остаётся пустым; интерфейс покажет `frontend/public/images/picture.png`. Импортёр не требует, чтобы изображения уже лежали на диске.

### Состав исходного импорта

В исходных XLSX: 20 пользователей, 31 карточка каталога, 35 размеров, 92 складских остатка, 10 заказов и 30 позиций заказов. В истории есть один товар, для которого нет карточки в `Products_import.xlsx`; импортёр создаёт для него минимальную карточку без изображения и подкатегории. Отличающееся уточнение в названии чёрных туфель связывается с существующей карточкой каталога, чтобы не создавать дубликат.

## Импорт исходных данных

Исходные XLSX-файлы находятся в `import_data/` в корне backend. Импорт запускается из корня проекта:

```bash
python -m scripts.import_data
```

Импортёр читает Excel, проверяет данные и создаёт записи через классы из `repositories/`. Прямые операции `session.add`, `session.exec` и `session.delete` в импортёре не используются; `Session` применяется для общей транзакции (`commit`/`rollback`).

Если таблицы уже содержат данные, импорт остановится. Полная замена данных выполняется только с явным флагом `--reset`:

```bash
python -m scripts.import_data --reset
```

API и скрипты читают параметры PostgreSQL из одного файла `config.toml`. Скрипт использует текущее складское количество из Excel как актуальное и не уменьшает его повторно на исторические заказы.


## Категории и подкатегории

Подкатегория принадлежит ровно одной категории (`subcategories.category_id`). Frontend запрашивает подкатегории только после выбора категории. Если в уже заполненной базе остались дубли из старого импорта, сначала сделайте резервную копию PostgreSQL, затем из корня backend выполните `python -m scripts.dedupe_categories`. Скрипт объединяет категории и подкатегории с одинаковыми названиями без учёта регистра и лишних пробелов, перепривязывает товары и удаляет дубли. Повторный импорт с `--reset` для этой задачи не требуется.

Файлы Excel для импорта находятся в `import_data/` в корне backend.
